## Inventory method and interpretation

Inspected HTTP route dispatch, server options, daemon protocol and command parser, native bridge declarations and implementation entry points, Telegram parsers and message dispatch, voice/WebRTC boundaries, and flake/NixOS definitions. Compared them with the pages registered by `docs/src/Documentation/Content.hs` and the separate engineering Markdown files.

**Coverage below means coverage in the user website.** Engineering notes are explicitly identified rather than counted as nonexistent. `Missing` therefore means absent from the website, not absent from the repository. `Covered` means a usable procedure exists for the bounded use case in that row, not that every implementation detail or failure path is documented.

Every row is **source-reviewed only** in this audit. Tests and header comments are corroborating specifications, not claims that those tests or interfaces were executed. No bot, account, server, microphone, deployment, or native application was started.

Original pre-remediation totals: **109 audit rows: 8 Covered, 15 Partial, 86 Missing**. Current totals are above. Rows have deliberately different granularity (individual HTTP routes versus native operation families), so these totals must not be presented as a percentage of product functionality.

At baseline, the website declared a terminal-client focus in `docs/README.md`. The remediation now adds server, native, daemon and deployment references. Remaining omissions are not proof that terminal documentation is defective; a claim that *all product functions* are documented must still account for the Partial rows and explicit unsupported/internal boundaries.

## Scope and residual questions

1. **Native applications:** repository traversal found bridge implementations and packaging, not native application UI source. Do not call Windows/iOS/Android/macOS application screens “missing documentation for implemented screens” without the respective application repository. Obtain those repositories for an application-level audit.
2. **Web interface:** this checkout contains the server HTTP API and documentation website, not evidence of a shipped browser conversation client. Web-client UI coverage remains outside what this checkout can establish.
3. **ABI depth:** all native export families are inventoried, but this is not a parameter-by-parameter ABI verification. The header is already a detailed developer contract; a supported-API policy is needed before translating every export into public product documentation.
4. **Server schema depth:** all dispatcher routes and explicit options are enumerated; nested request/response fields, every status code and every SSE payload must be generated or audited from OpenAPI and types in a follow-up reference pass.
5. **Deployment validation:** no production credentials, NixOS VM, Telegram bot, microphone or native app was available or exercised in this audit. Existing source tests do not justify live-operation claims.
6. **Engineering notes versus website:** promoting `docs/agent-server.md`, `docs/runtime-daemon-protocol.md`, `docs/telegram.md`, `docs/nixos.md`, and native engineering material is cheaper and more accurate than authoring from scratch. Each still requires source reconciliation.
